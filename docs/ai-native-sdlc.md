# AI-Native SDLC — intent.md 도입 가이드

코드를 쓰기 전에 **무엇을 왜 만드는지** 먼저 저장소에 남기고, 그 문서를 다음 단계의 입력으로 쓰는 방식.

**출처**: [intent.md로 시작하는 AI 네이티브 SDLC 플레이북 가이드](https://www.digitalmarketer.co.kr/insights/intent-md-ai-native-sdlc-playbook-guide) (digitalmarketer.co.kr).
이 글은 Anthropic의 "AI 네이티브 SDLC 플레이북"(2026-08-21 공개)을 소개한 2차 자료다 —
아래 내용은 그 기사 기준으로 정리했고, 원문 플레이북은 직접 확인하지 않았다.

---

## 1. 왜 이걸 도입하나

이 저장소의 커밋 메시지는 이미 "무엇을 고쳤나"가 아니라 **"왜 그렇게 고쳤나"**를 길게 적는다.
예를 들어 `96d36b9`(오더 복구)는 왜 복구 분기가 `diffChanged` 앞에 와야 하는지,
왜 `is_dual_assignment`와 `assignee_tester_id_2`를 한 UPDATE에 담아야 하는지를 본문에 남겼다.

문제는 **그 판단이 코드를 다 쓴 뒤에야 기록된다**는 점이다. 그래서 이런 일이 반복됐다.

| 실제로 있었던 일 | 원인 |
|---|---|
| 월간 스케줄이 3개월 가까이 빈 화면 (`72a38c8`에서 수정) | 구 화면 삭제 시 스냅샷 기록 경로가 함께 사라진 것을 아무도 몰랐다 |
| 미배정 오더를 확정(LOCK)하면 배정이 영구 불가 | "확정"의 전제조건을 적어 둔 곳이 없었다 |
| 복구가 담당자·확정을 지운다는 사실 | 커밋 메시지에만 있어, 화면을 쓰는 사람은 알 수 없었다 |

intent.md는 이 판단을 **착수 전에**, **코드와 같은 저장소에** 남긴다.
목적은 문서를 늘리는 게 아니라, 다음 세 가지를 얻는 것이다.

1. **범위 고정** — "이번엔 여기까지"가 글로 있으면 작업이 번지지 않는다.
2. **미결정 사항의 명시** — 모르는 걸 `Open questions`에 적어두면 AI가 그것부터 되묻는다.
3. **변경 근거의 추적** — 제약 QC 시스템이라 "이 기능이 왜 이렇게 동작하나"를 되짚을 일이 잦다.
   `Status` 이력이 그 근거가 된다. (GMP 요건 충족을 주장하는 건 아니다 — 되짚기가 쉬워진다는 뜻이다.)

## 2. 이 프로젝트에 맞춘 형태

기사는 팀 규모를 전제로 6단계(intent → spec → plan → test → deploy → maintain)를 제시한다.
이 저장소는 사실상 1인 개발이므로 **3단계로 줄여서 쓴다.**

| 기사의 단계 | 이 프로젝트에서 | 이유 |
|---|---|---|
| `intent.md` | **필수** | 유일하게 생략 불가 |
| `spec.md` | **생략** (아래 예외만) | 1인 작업에서 설계 문서를 따로 두면 코드와 즉시 어긋난다 |
| `plan.md` | **플랜 모드 승인으로 대체** | Claude Code 플랜 모드가 파일 목록·순서·위험을 이미 보여준다 |
| 테스트 | `npm run typecheck` (필수) | 자동 테스트 스위트가 없다 — `AGENTS.md` > Testing Requirements |
| 배포 | main push → Railway 자동 배포 | `577e908` |
| 유지 | 새 intent 작성 | 진단 결과를 다음 intent의 `Problem`으로 넣는다 |

### spec.md를 쓰는 유일한 예외

다음 중 하나에 해당하면 `intent/` 안에 `-spec.md`를 같이 둔다.

- **DB 마이그레이션을 동반**하는 변경 (`supabase/migrations/`에 파일이 늘어남)
- **권한·인증 규칙**을 건드리는 변경 (`backend/lib/guard.ts`, `types/route-access.ts`, RLS)
- **확정(LOCK)·상태 전이 규칙**을 건드리는 변경 (`types/qc-status.ts`, `pctOrders.ts`의 불변식)

이 세 가지는 잘못되면 되돌리기가 어렵고, 실제로 사고가 났던 영역이다.
(`0038_dual_assignment_invariants.sql`의 CHECK 제약, `testerLink.ts`의 2026-08-23 보안 수정이 그 흔적이다.)

## 3. intent.md 작성 규칙

### 파일 위치와 이름

```
intent/YYYY-MM-DD-슬러그.md
```

- 예: `intent/2026-09-11-side-work-tester-access.md`
- 슬러그는 영문 kebab-case (파일명은 영어, **내용은 한국어**)
- 템플릿: [`intent/TEMPLATE.md`](../intent/TEMPLATE.md)

### 5개 섹션 — 이것만 쓴다

| 섹션 | 내용 | 자주 하는 실수 |
|---|---|---|
| `Problem` | 지금 무엇이 불편한가 | 해결책을 여기 쓴다 |
| `Proposed outcome` | 해결되면 무엇이 달라지는가 | 화면 문구까지 확정하려 든다 |
| `Affected users and systems` | 영향받는 사용자·화면·테이블 | 테이블을 안 적는다 (이 프로젝트에선 필수) |
| `Constraints` | 예산·기한·정책·금지사항 | "없음"으로 비운다 |
| `Open questions` | 아직 정하지 못한 것 | 비워 둔다 — **비면 안 된다** |

머리에는 `Author`와 `Status`를 적는다.

### 절대 규칙 — "어떻게"는 쓰지 않는다

intent.md에 **기술 선택과 구현 방법을 쓰지 않는다.** 그건 플랜 모드의 몫이다.

| ✗ 쓰지 않는다 | ✓ 이렇게 쓴다 |
|---|---|
| "`canEditCell`에 `myTesterId` 비교를 추가한다" | "시험자가 자기 칸만 고칠 수 있어야 한다" |
| "`side_work_logs` 테이블을 만든다" | "시험 외 업무를 날짜별로 남길 수 있어야 한다" |
| "useMemo로 캐싱한다" | "달을 넘길 때 눈에 띄는 지연이 없어야 한다" |

이유: 구현 방법을 미리 못 박으면 코드베이스를 읽은 뒤에야 보이는 더 나은 방법이 막힌다.
실제로 월간 스케줄은 "스냅샷 기록을 복구한다"(B안)보다 "`pct_orders` 직독으로 바꾼다"(A안)가 옳았고,
그 판단은 코드를 읽고 나서야 나왔다.

### Status 흐름

```
draft  →  approved  →  completed
```

- **삭제하지 않는다.** 폐기하면 `abandoned`로 바꾸고 이유를 한 줄 남긴다.
- `draft → approved`: 착수 승인. 이 시점에 **intent 파일을 먼저 커밋**한다.
- `approved → completed`: 구현 완료. **코드와 같은 커밋**에서 Status를 바꾼다.
  이렇게 해야 문서가 낡지 않는다.

### `Affected users and systems`에 반드시 적을 것

이 프로젝트 특성상 아래를 빠뜨리면 작업 중에 반드시 막힌다.

- **역할**: 관리자 / 시험자 / 둘 다 — 권한 분기가 거의 모든 화면에 있다
- **테이블**: 건드리는 Supabase 테이블 이름
- **확정(LOCK)·작업 시작 상태와의 관계**: 그 오더가 LOCK이면 어떻게 되나
- **크론**: `instrumentation.ts`에 등록된 셋 중 무엇에 닿나 —
  PCT 적재 09:00/14:00, 장비 대기(WAITING) 24시간 초과 자동취소 매시 정각

## 4. 작성 방법 — 직접 쓰지 말고 인터뷰를 받는다

빈 템플릿을 채우려 하면 `Open questions`가 비고 `Constraints`가 "없음"이 된다.
대신 **Claude에게 인터뷰를 시킨다.**

```
/intent 시험자가 월간 그리드에서 부업무를 남기게 하고 싶어
```

`/intent` 슬래시 커맨드([`.claude/commands/intent.md`](../.claude/commands/intent.md))가 다음을 한다.

1. 한 번에 하나씩 묻는다 — 범위 → 사용자·역할 → 영향 테이블 → 제약 → 미결정
2. 코드베이스를 읽고 **당신이 모르는 제약을 먼저 알려준다**
   (예: "확정된 오더는 `LOCKED_IMMUTABLE_FIELDS` 때문에 담당자 변경이 막힙니다 — 부업무도 같은 규칙인가요?")
3. 질문이 끝나면 `intent/YYYY-MM-DD-슬러그.md`를 써서 보여준다
4. **거기서 멈춘다** — 코드는 건드리지 않는다

### 작성된 intent를 검토할 때 볼 것

- `Proposed outcome`에 **내가 말하지 않은 기능**이 들어가 있지 않은가
- `Open questions`가 **실제로 안 정해진 것**인가 (형식만 채운 질문은 지운다)
- `Constraints`에 "기존 동작을 깨지 않는다"가 아니라 **구체적으로 무엇을** 깨지 않는지 적혔는가

## 5. 구현 단계로 넘기는 방법

승인(`Status: approved`) 후, 새 대화에서:

```
intent/2026-09-11-side-work-tester-access.md 를 읽고 플랜을 세워줘.
AGENTS.md 규칙을 지키고, Open questions 는 구현 전에 먼저 물어봐.
```

플랜 모드가 파일 목록·순서·위험을 내놓으면 승인하고 진행한다. (`plan.md`는 만들지 않는다.)

**완료 조건** — 아래를 모두 만족해야 `completed`로 바꾼다.

- `npm run typecheck` 통과 (필수)
- `npm run lint`
- 운영 영향이 있으면 `npm run build`
- `Open questions`가 전부 해소되었거나, 남은 것이 intent 파일에 결론과 함께 기록됨

## 6. 기존 문서와의 관계

문서가 겹치면 아무도 안 읽는다. 역할을 이렇게 나눈다.

| 문서 | 시점 | 범위 | 성격 |
|---|---|---|---|
| `intent/*.md` | **앞으로** 만들 것 | 변경 **하나** | 착수 전 의도 |
| `docs/PRD-current-system.md` | **이미** 만들어진 것 | 시스템 **전체** | as-built 현황 |
| `docs/WORKFLOW-current-system.md` | 이미 만들어진 것 | 단계별 동작 흐름 | as-built 현황 |
| `.claude/commands/qc-schedule-process.md` | 확정된 요구사항 | PCT 워크플로우 | 프로세스 단일 기준 |
| `AGENTS.md` | 항상 | 코딩 규칙 | 컨벤션 |
| 커밋 메시지 | 사후 | 변경 하나 | 왜 그렇게 고쳤나 |

**중복 금지 규칙**: intent가 `completed`가 된 뒤 시스템 전체 설명이 달라졌으면
`docs/PRD-current-system.md`를 갱신한다. intent 파일에 시스템 전체 설명을 늘려 쓰지 않는다.

## 7. 언제 intent를 건너뛰나

전부에 intent를 요구하면 아무도 안 쓴다. **다음은 그냥 한다.**

- 오타·문구 수정, 색/간격 등 디자인 표준 적용
- 명백한 버그 수정으로 **동작 규칙이 바뀌지 않는** 것
  (예: 하이드레이션 경고 제거, 스크롤 컨테이너 높이 수정)
- 리팩터링으로 **겉보기 동작이 그대로**인 것

**반대로 intent가 반드시 필요한 것:**

- 새 화면·새 메뉴 항목
- 새 테이블 또는 마이그레이션
- 권한 규칙 변경 (누가 무엇을 할 수 있나)
- 상태 전이·확정(LOCK) 규칙 변경
- 외부 연동 추가 (슬랙·구글시트·AI 공급자)
- 크론·자동 실행 추가

## 8. 작성 예시 (실제 사례 역산)

아래는 `72a38c8`(월간 스케줄 전환)을 **작업 전에 썼다면** 이렇게 됐을 모습이다.
설명용 예시이며 실제 `intent/` 파일은 아니다.

```markdown
# Intent: 월간 스케줄을 오더 기준으로 다시 그린다
Author: kyo (개발) · Status: draft

## Problem
월간 QC 시험 스케줄 화면이 어느 달을 열어도 "배정된 스케줄이 없습니다"만 뜬다.
AI 스케줄 화면에는 배정이 19건 보이는데 월간에는 0건이다. 사용자는 월간 화면을
신뢰하지 않게 되어 주간 화면만 쓰고 있다.

## Proposed outcome
월간 화면이 AI 스케줄 화면과 같은 배정을 보여준다. 달을 넘겨도 그 달의 배정이 나온다.
2인 배정은 담당자 양쪽 행에 모두 나타난다.

## Affected users and systems
- 역할: 관리자·시험자 둘 다 (읽기)
- 화면: `/schedule/monthly`
- 테이블: `pct_orders`(정본), `qc_jobs`(실제 착수일), `product_workload`(공수), `schedules`(레거시 — 읽기 중단 대상)
- 확정(LOCK) 관계: 없음 (읽기 전용 화면)
- 크론: 영향 없음

## Constraints
- 레거시 `schedules` 테이블은 건드리지 않는다 (2026-04 데이터 65행 보존).
- 주말·공휴일은 일정 길이 계산에서 제외한다.
- 사람마다 다른 화면이 보이면 안 된다 — 브라우저 저장소를 근거로 쓰지 않는다.

## Open questions
- 한 배정이 달력의 어느 날짜들을 차지하는가? 착수일 기준인가 포장일 기준인가?
- 공수 정보가 없는 품목은 며칠로 그리나?
- 레거시 `schedules`의 기존 65행을 화면에서 계속 보여줘야 하나?
```

`Open questions`의 첫 질문이 실제로 이 작업의 핵심이었고, 최종 구현은
"① 착수했으면 `qc_jobs.work_start_date` ② 아니면 포장일 다음 근무일 ③ 포장일 없으면 납기 역산"으로 답했다.
이 질문을 미리 적어두면 구현이 그 답부터 시작한다.

> **각주**: 이 사례는 `72a38c8` 한 번으로 끝나지 않고 다음 날 `44d59ee`(*월간 스케줄이 사람마다 다르게
> 보이던 문제 — 서버 정본 하나만 읽는다*)로 한 번 더 수정됐다. 위 예시의 `Constraints` 마지막 줄
> ("사람마다 다른 화면이 보이면 안 된다 — 브라우저 저장소를 근거로 쓰지 않는다")이 바로 그 두 번째 수정의
> 내용이다. **제약에 미리 적혔더라면 커밋 하나로 끝났을 일**이라 예시에 남겨 뒀다.
