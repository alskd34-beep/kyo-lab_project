# [3] 검증 게이트 — 코드로 구현할 것 (프롬프트 아님)

> **이 단계를 LLM에게 맡기지 마라.** 프롬프트의 보안 규칙은 "대체로" 지켜지고,
> 대체로는 보안이 아니다. 아래는 모델 출력을 **실행 전에 코드로** 검사하는 목록이다.
> 검사 실패 시 → 사유를 담아 [2]단계 재시도(최대 1~2회) → 그래도 실패하면 사용자에게 실패 보고.

## A. 구문 화이트리스트

- [ ] 최상위가 `SELECT` 또는 `WITH ... SELECT` 인가
- [ ] 세미콜론으로 분리된 **멀티 스테이트먼트**가 아닌가
- [ ] 금지 키워드 부재: `INSERT` `UPDATE` `DELETE` `MERGE` `REPLACE` `CREATE` `ALTER`
      `DROP` `TRUNCATE` `GRANT` `SET` `CALL` `LOAD` `OUTFILE` `INFILE`
- [ ] 지연 함수 부재: `SLEEP` `BENCHMARK` `WAITFOR`
- [ ] 시스템 스키마 접근 부재: `information_schema` `mysql.*` `performance_schema` `pg_catalog`
- [ ] 주석 시퀀스(`--` `/*` `#`)로 조건을 무력화하지 않았는가

> 문자열 리터럴 안의 키워드를 오탐하지 않도록, **리터럴을 먼저 마스킹한 뒤** 검사한다.

## B. 스키마 정합성

- [ ] 등장하는 모든 테이블이 카탈로그에 실재하는가
- [ ] 등장하는 모든 컬럼이 해당 테이블에 실재하는가
- [ ] 조인 조건이 정의된 관계 키를 쓰는가 (임의 조인 차단)

## C. 테넌트 경계 (멀티테넌트일 때 — 가장 중요)

- [ ] 테넌트 키 동등 조인으로 연결된 **묶음마다 `= ?` 루트가 정확히 하나**인가
      (0개 → 데이터 유출 / 2개 이상 → 중복 바인딩 거부)
- [ ] 모든 물리 테이블이 루트에 직접 또는 동등 조인으로 연결되는가 (고아 테이블 = 유출)
- [ ] 테넌트 키에 **리터럴 값이 하드코딩**되지 않았는가 (`= '값'`, `IN (...)` 차단)
- [ ] `?` 총개수 == 묶음 수이고, 테넌트 바인딩 외의 `?` 가 없는가
- [ ] `LEFT JOIN` 별칭의 테넌트 키가 `WHERE` 로 올라가 `INNER JOIN` 이 되지 않았는가
- [ ] 테넌트 키 없는 공용·개인 테이블을 조회하지 않는가

> 바인딩은 **서버가 채운다.** 모델은 `?` 자리만 만들고, 실제 값은 세션에서 주입한다.
> 모델이 만든 문자열에 테넌트 값을 포맷팅해 넣는 순간 이 게이트는 무의미해진다.

## D. 권한 게이트

- [ ] 현재 사용자의 허용 메뉴/역할로 접근 가능한 테이블만 쓰는가
- [ ] 민감 컬럼(암호화 PII 등)이 허용 목록 안인가
- [ ] 복호화 함수(`AES_DECRYPT` `DECODE` `FROM_BASE64` 등) 부재 — 복호화는 출력 단계 책임

## E. 실행 안전

- [ ] 결과 행 상한(`LIMIT`)이 강제되는가 — 없으면 서버가 주입
- [ ] 쿼리 타임아웃이 설정돼 있는가
- [ ] 읽기 전용 커넥션/계정으로 실행하는가 (**DDL·DML 권한 자체가 없는 계정**)

> E의 마지막 항목이 진짜 마지막 방어선이다. A~D를 전부 뚫려도
> 읽기 전용 계정이면 데이터가 파괴되지 않는다.

## F. 금지 주제 필터 (선택)

- [ ] 질문·응답에 조직이 정의한 금지 주제가 포함되는가 → 정해진 안내문으로 대체

## 재시도 피드백 설계

재시도할 때 "다시 해봐"가 아니라 **무엇이 왜 틀렸는지**를 [2]단계에 돌려준다.

```
[이전 시도 실패]
생성된 쿼리: <원문>
검증 실패: C-1 — 별칭 t2, t3 이 테넌트 루트에 연결되지 않았습니다.
수정 지침: t2.{{TENANT_KEY}} = t1.{{TENANT_KEY}} 동등 조인을 추가하되
           별도 ? 바인딩은 추가하지 마십시오.
```

실패 사례는 bad-example 로 축적해서 다음 요청의 few-shot 에 넣으면
같은 실수의 재발이 눈에 띄게 줄어든다.
