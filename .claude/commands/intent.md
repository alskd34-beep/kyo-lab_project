# /intent — 착수 전 의도 문서 작성 (인터뷰)

> **"intent 써줘" / "의도 문서" / `/intent` 라고 하면 이 문서를 따른다.**
>
> 전체 방법론: `docs/ai-native-sdlc.md` · 템플릿: `intent/TEMPLATE.md`

코드를 쓰기 전에 `intent/YYYY-MM-DD-슬러그.md` 를 만드는 절차.
사용자가 `/intent <하고 싶은 일>` 로 호출한다. 인자가 없으면 무엇을 만들고 싶은지 먼저 묻는다.

---

## 이 커맨드가 지켜야 할 것

1. **코드를 절대 수정하지 않는다.** 이 커맨드의 산출물은 intent 파일 **하나**뿐이다.
2. **한 번에 하나씩 묻는다.** 질문을 묶어서 던지지 않는다 — 사용자가 답하기 어려워진다.
3. **먼저 코드베이스를 읽는다.** 사용자가 모르는 제약을 찾아서 질문에 녹인다.
4. **"어떻게"를 쓰지 않는다.** 기술 선택·구현 방법·파일명·함수명은 intent에 넣지 않는다.
5. 파일을 쓰고 **멈춘다.** 구현으로 넘어가지 않는다. 승인은 사람이 한다.

---

## 절차

### 0단계 — 코드베이스 선행 조사 (질문 전에)

사용자의 요청과 관련된 영역을 먼저 읽고, **사용자가 모를 만한 제약**을 찾아둔다.
질문을 시작하기 전에 이걸 하는 이유: 모르면 질문이 뻔해지고, 뻔한 질문은 `Open questions`를 비우게 만든다.

확인할 것:
- 관련 화면의 권한 분기 (`isAdmin`, `user.testerId`, `types/route-access.ts`)
- 건드릴 테이블과 그 불변식 (`supabase/migrations/` 의 CHECK 제약, RLS)
- 확정(LOCK)·작업 시작 상태가 막는 것 (`LOCKED_IMMUTABLE_FIELDS`, `STARTED_IMMUTABLE_FIELDS`, `types/qc-status.ts`)
- 크론·적재 경로에 닿는지 (`instrumentation.ts`, `backend/services/pctIngest.ts`)

### 1단계 — 범위

"이번에 어디까지 하고, 어디는 안 할 것인가"를 묻는다.
사용자가 넓게 말하면 **자르는 선을 제안**한다.

### 2단계 — 사용자와 역할

누가 쓰는가. **관리자인가 시험자인가 둘 다인가.**
이 프로젝트는 권한 분기가 거의 모든 화면에 있으므로 이 질문을 건너뛰지 않는다.
(예: 부업무 기능은 "관리자는 되는데 시험자는 안 되는" 문제가 실제로 났다.)

### 3단계 — 영향 범위

0단계에서 찾은 것을 근거로 확인받는다. 이때 **알아낸 제약을 알려주면서** 묻는다.

> 예) "확정(LOCK)된 오더는 `assigneeTesterId`가 변경 불가 필드라 담당자 배정이 막힙니다.
> 이번에 추가할 기능도 확정된 오더에서는 막혀야 합니까, 아니면 확정과 무관합니까?"

### 4단계 — 제약

예산·기한·정책·금지사항. "없음"이라고 답하면 아래를 되짚어 구체화한다.
- 기존 데이터 중 보존해야 하는 것
- 깨지면 안 되는 기존 동작 (구체적으로 무엇)
- 성능·응답 속도 기준
- 사람마다 다르게 보이면 안 되는 것 (브라우저 저장소를 근거로 쓰면 안 되는 자리)

### 5단계 — 미결정 사항

"지금 결정 못 한 게 무엇인가"를 묻는다.
사용자가 "없다"고 해도, 0단계에서 찾은 것 중 **답이 정해지지 않은 것**을 여기로 옮긴다.
`Open questions`가 비어 있는 intent는 잘못 쓰인 것이다.

### 6단계 — 파일 작성

`intent/YYYY-MM-DD-슬러그.md` 로 쓴다. 날짜는 오늘, 슬러그는 영문 kebab-case, **내용은 한국어**.
`intent/TEMPLATE.md` 의 5개 섹션 구조를 그대로 따른다.

**`-spec.md` 가 추가로 필요한 경우** — 아래 셋 중 하나에 해당하면 그 사실을 사용자에게 알린다.
(파일 자체는 승인 후 구현 단계에서 만든다. 이 커맨드는 intent 하나만 쓴다.)

- DB 마이그레이션 동반 — `supabase/migrations/` 에 파일이 늘어남
- 권한·인증 규칙 변경 — `backend/lib/guard.ts`, `types/route-access.ts`, RLS
- 확정(LOCK)·상태 전이 규칙 변경 — `types/qc-status.ts`, `pctOrders.ts` 의 불변식

작성 후 사용자에게 이렇게 알린다.

- 파일 경로
- **내가 추측으로 채운 부분**이 있으면 어디인지 (사용자가 말하지 않은 것을 넣었다면 반드시 밝힌다)
- 위 `-spec.md` 조건에 걸리는지 여부
- 검토 포인트 3개: ① 말하지 않은 기능이 들어갔는지 ② `Open questions`가 진짜 미결정인지 ③ `Constraints`가 구체적인지
- 다음 단계: 승인하면 `Status: approved` 로 바꾸고 intent 를 먼저 커밋한다.
  흐름은 `draft` → `approved` → `completed` 이며, **폐기할 때도 파일을 지우지 않고** `abandoned` 로 바꾸고 이유를 한 줄 남긴다.

### 7단계 — 멈춘다

구현하지 않는다. 플랜도 세우지 않는다. 사용자가 승인한 뒤 **새 대화**에서 진행한다.

---

## intent를 만들지 말아야 할 때

요청이 아래에 해당하면 intent를 만들지 말고 **그렇게 말한 뒤 바로 작업을 제안**한다.

- 오타·문구 수정, 색·간격 등 디자인 표준 적용
- 동작 규칙이 바뀌지 않는 명백한 버그 수정
- 겉보기 동작이 그대로인 리팩터링

반대로 아래는 사용자가 `/intent` 를 안 썼더라도 **intent를 먼저 쓰자고 제안**한다.

- 새 화면·새 메뉴 항목
- 새 테이블 또는 마이그레이션
- 권한 규칙 변경
- 상태 전이·확정(LOCK) 규칙 변경
- 외부 연동 추가 (슬랙·구글시트·AI 공급자)
- 크론·자동 실행 추가

---

## 구현으로 넘어갈 때 (참고 — 이 커맨드의 일이 아니다)

승인 후 **새 대화**에서:

```
intent/<파일> 을 읽고 플랜을 세워줘.
AGENTS.md 규칙을 지키고, Open questions 는 구현 전에 먼저 물어봐.
```

완료 시 `Status: completed` 를 **코드와 같은 커밋**에서 바꾼다.
완료 조건 전체는 `docs/ai-native-sdlc.md` §5 를 따른다(여기에 다시 적지 않는다).
