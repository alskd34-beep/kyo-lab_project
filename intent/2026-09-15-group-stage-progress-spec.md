# Spec: 동시분석 그룹 단계 일괄 진행 — 그룹 검토·그룹 승인 규칙
Author: kyo (개발) · Status: completed
관련 intent: [2026-09-15-group-stage-progress.md](./2026-09-15-group-stage-progress.md)
근거: 감독 결정 `temp/decisions-t1-t3.md`(공통·T1 — **단일 기준**) · 탐색 브리프 `temp/brief-t1-group-stage.md`
선행 규칙: [시험항목 단위 검토 spec](./2026-09-15-item-level-review-spec.md)(검토 전제·단계 도출·이력) ·

이 문서는 관리자가 동시분석 그룹의 **한 배치에서 누른 검토·승인이 그룹의 어느 배치에, 어떤 조건으로 적용되고,
무엇이 기록되는가**를 못박는다. 그룹 검토의 최종 판정은 DB 함수(마이그레이션 0051)가, 그룹 승인의 최종 판정은
배치마다 기존 승인 경로가 한다. 화면의 버튼 노출·대상 배치 목록은 같은 규칙의 보조 판정일 뿐이다.

표기
- 무표시 = 결정 문서에 있는 규칙.
- **[브리프 준용]** = 결정이 정하지 않았고 브리프 권고가 결정과 충돌하지 않아 옮긴 세부.
- **[현행 유지]** = 지금 코드의 규칙·문구를 그대로 이어 쓰는 것.
- **[구현]** = 구현하면서 정한 세부(§11 에 이유).

## 1. 전파 대상

| 기준 | 규칙 |
|---|---|
| 그룹 구성 | 서버가 **조작 시점**에 `concurrent_analysis_group_items.group_id = 그룹` 인 오더 전부를 다시 읽는다. 화면이 보던 배치 목록은 참고일 뿐이다 |
| 대상 작업 | 그 오더들의 **모든 `qc_jobs`**(담당자 무관 — 병렬 배정 담당자별 작업 포함). 작업을 시작하지 않은 오더는 작업이 없어 대상이 아니다 |
| 항목 매칭(항목 단위) | `qc_job_items.test_item_name = 요청 항목명`(정확히 같은 문자열). 그 이름이 없는 작업은 **조용히 건너뛴다**(skipped 에 넣지 않음). unique 가 아니므로 한 작업에 같은 이름이 여럿이면 모두 대상 |
| 항목 매칭(일괄) | 검토 시작 = 각 작업의 `cleared`+`none` 항목 전부 / 검토 완료 = 각 작업의 `reviewing` 항목 전부. 대상 항목이 없는 작업은 조용히 건너뛴다 |
| 진입 배치 | 화면에서 누른 작업·항목은 **진입점일 뿐**, 서버 판정에 특별 대우가 없다 |
| 멤버 1건 그룹 | 오더가 2건 미만인 그룹은 서버가 거절하고(§4), 화면은 그룹 버튼을 보이지 않는다. 화면은 그룹의 **시작된 작업이 2건 이상**일 때만 그룹 버튼을 보인다 [구현] |

## 3. 배치별 판정 (그룹 검토 — DB 함수 안)

그룹 검토는 작업마다 아래를 **순서대로** 보고, 처음 걸린 사유로 그 (작업, 항목)을 건너뛴다. 전체를 거절하지 않는다.

| # | 조건 | 결과 | skipped `reason`(전문) |
|---|---|---|---|
| S1 | 잠그려는 사이 작업 행이 사라짐(작업 시작 취소 커밋) | 그 작업 건너뜀 | `작업이 삭제되었습니다` |
| S2 | 대상 항목이 없음(이름 없음 / 일괄 대상 0건) | 조용히 건너뜀 | (skipped 에 넣지 않음) |
| S3 | 작업이 `승인완료` | 그 작업의 대상 항목 전부 건너뜀 | `승인완료 작업` |
| S4 | `review_start`: 항목 `status ≠ cleared` | 건너뜀 | `시험이 끝나지 않음` |
| S5 | `review_start`: 항목 `review_status = reviewing` | 건너뜀(멱등) | `이미 검토 중` |
| S6 | `review_start`·`review_complete`: 항목 `review_status = reviewed` | 건너뜀(멱등) | `이미 검토 완료` |
| S7 | `review_complete`: 항목 `review_status = none` | 건너뜀 | `검토를 시작하지 않음` |

- 일괄 모드는 대상을 이미 `cleared+none` / `reviewing` 으로 골랐으므로 S3 만 실제로 걸린다.
- `지연` 작업은 건너뛰지 않는다 — 검토는 허용하고 단계는 `지연` 을 유지한다(`recompute_job_stage` 규칙 0).
- S4~S7 판정을 통과한 항목에만 `apply_item_review_step` 을 부른다. 그 함수의 전제 검사(0048 §3.2 조건 5)와 같은 규칙이므로
  정상 경로에서 그 함수가 거절하는 일은 없다. 만약 거절하면(규칙 불일치 버그) **그룹 전체가 롤백**된다.

판정 순서: 0 → 1 → 2 → 3 → (잠금·배치별 판정) → 4. 거절은 `errcode P0001`, 서비스가 메시지를 그대로 보인다.

| # | 조건 | 거절 메시지(전문) |
|---|---|---|
| 0 | 동작 값이 `review_start`·`review_complete` 가 아님 | `알 수 없는 검토 동작입니다.` (단건 문구와 같다 [현행 유지]) |
| 0' | 항목 단위인데 항목명이 비었음 | `시험항목명을 입력해 주세요.` |
| 1 | 요청자가 활성 관리자가 아님(라우트 `requireAdmin` + 함수 `users.role='admin' AND is_active`) | `관리자만 시험항목을 검토할 수 있습니다.` [현행 유지] |
| 2 | 그룹 없음(없는 id·잘못된 uuid) | `동시분석 그룹을 찾을 수 없습니다.` |
| 3 | 그룹 오더가 2건 미만 | `동시분석 그룹에 배치가 2건 이상일 때만 그룹으로 처리할 수 있습니다.` |
| 4 | 처리한 항목이 0건(대상 없음 또는 전부 건너뜀) | `처리할 시험항목이 없습니다.` — 이력·단계 변화 없음 |
| — | 0051 미적용(`PGRST202`/`42883`) | `동시분석 그룹 검토 기능의 DB 설치(0051 마이그레이션)가 아직 적용되지 않았습니다. 관리자에게 문의하세요.` |
| — | 교착 재시도 후에도 교착 | `다른 작업과 동시에 처리되어 저장하지 못했습니다. 잠시 후 다시 시도해 주세요.` [현행 유지 — rpcRetry] |
| — | 그 밖의 DB 오류 | 전체 롤백. `시험항목 검토 처리 중 DB 오류가 발생했습니다. 관리자에게 문의하세요. (원인: …)` [현행 유지] |

## 5. 원자성·잠금 순서 (그룹 검토)

### 5.1 RPC 시그니처

| 함수 | 시그니처 | 반환 |
|---|---|---|
| 내부 | `group_review_apply(p_group_id uuid, p_test_item_name text, p_user_id uuid, p_action text) returns jsonb` — `p_test_item_name` 이 null 이면 일괄 | 아래와 같음 |
| 항목 단위 | `group_item_review_action(p_group_id uuid, p_test_item_name text, p_user_id uuid, p_action text) returns jsonb` | `groupId`·`action`·`testItemName`·`count`(처리 항목 수)·`processed[]`·`skipped[]`·`stages[]` |
| 일괄 | `group_item_review_bulk_action(p_group_id uuid, p_user_id uuid, p_action text) returns jsonb` | 같음(`testItemName` null) |

- `processed[]` 원소: `jobId`·`orderId`·`qcNo`·`batchNo`·`itemId`·`testItemName`·`reviewStatusBefore`·`reviewStatusAfter`
- `skipped[]` 원소: `jobId`·`qcNo`·`batchNo`·`testItemName`·`reason`(§3 전문)
- `stages[]` 원소: 건드린(처리 항목이 1건 이상인) 작업마다 `recompute_job_stage` 반환값 1개

### 5.2 처리 순서 — 함수 한 번 = 한 트랜잭션

| 단계 | 동작 |
|---|---|
| ① | 동작 값·항목명·관리자 확인(§4 0·0'·1) |
| ② | 그룹 존재(§4-2), 그룹 오더 읽기, 2건 미만 거절(§4-3) — **그룹 테이블은 잠그지 않는다**(§5.4) |
| ③ | 그 오더들의 작업 id 를 **id 오름차순**으로 읽는다(잠금 전) |
| ④ | 작업 행을 **id 오름차순으로 하나씩 `for update`**. 사라진 작업은 S1 |
| ⑤ | 잠근 작업마다 차례로: 그 작업의 `qc_job_items` 행 전부 `for update` → 대상 항목 선택(순번·생성 순) → §3 판정 → 통과 항목에 `apply_item_review_step` → 처리 항목이 1건 이상이면 `recompute_job_stage` |
| ⑥ | 처리 0건이면 §4-4 거절(롤백) |
| ⑦ | 반환. (커밋 뒤) 서비스가 `stages[]` 중 `changed` 인 것마다 기존 `notifyStageRecomputed`(오더 동기화 → 슬랙 → 앱 알림) |

- 잠금 순서: **모든 그룹 작업(`qc_jobs`, id 오름차순) → 각 작업의 `qc_job_items`**. 전역 순서
  `qc_jobs < pct_orders < pct_order_assignees < pct_order_test_items < qc_job_items`(0050) 를 어기지 않는다.
  작업 행을 모두 잡은 뒤에 항목 행을 잡으므로, 다른 작업의 항목을 잡은 채 작업 행을 기다리는 일이 없다.
- 작업 목록을 잠그기 전에 읽으므로, 그 사이 새로 시작된 작업은 이번 조작에 들어가지 않는다(새 작업은 항목이 `pending` 이라 어차피 검토 대상이 없다).
- 항목은 **작업 행을 잠근 뒤** 그 작업 id 로 읽는다. F2 항목 이동은 같은 오더의 두 작업 행을 먼저 잠그므로, 이 함수가 그룹 작업 행을
  쥐는 동안에는 대상 항목이 옮겨질 수 없다 — 단건 함수의 조건 3'(잠금 전후 작업 비교)는 필요 없다.
- `recompute_job_stage` 는 이미 잡은 작업·항목 행을 재진입한다(새 잠금 없음).

### 5.3 GMP — 배치별 기록

- 검토 이력 `qc_job_item_review_history` 는 **처리한 (작업, 항목)마다 1행**이다(`apply_item_review_step` 이 쓴다). `qc_job_id`·`order_id`·`qc_no` 는 그 배치의 값이고,
  `changed_by`·`changed_by_name` 은 요청 관리자다. "그룹 1건" 기록은 만들지 않는다.
- 단계 이력 `qc_job_status_history` 는 단계가 실제로 바뀐 **작업마다 1행**(source `auto`). note:
  - 항목 단위: `시험항목 "{항목명}" {검토 시작으로|검토 완료로} 서버가 자동 전환했습니다. (동시분석 그룹 일괄)`
  - 일괄: `시험항목 {n}개 {검토 시작으로|검토 완료로} 서버가 자동 전환했습니다. (동시분석 그룹 일괄)` — n 은 **그 작업에서** 처리한 항목 수
- 건너뛴 배치는 아무 기록도 남기지 않는다(실패가 아니다).

### 5.4 경합

| 경합 | 결과 |
|---|---|
| 같은 그룹에 두 관리자가 동시에 [그룹 검토 시작] | 둘째는 첫 작업 행에서 대기 → 첫째 커밋 뒤 전부 S5(`이미 검토 중`) → 처리 0건이면 §4-4 거절 |
| 그룹 검토 ↔ 단건 검토(같은 배치) | 작업 행 잠금으로 직렬화. 뒤에 온 쪽이 멱등 skip(그룹) 또는 조건 5 거절(단건) |
| 그룹 검토 ↔ 시험자 항목 완료 | 항목 완료 update 는 단일 문장이라 먼저 커밋되면 그 항목이 대상에 들어오고, 나중이면 S4. 단계는 두 쪽 재도출이 수렴 |
| 그룹 검토 ↔ 작업 시작 취소(0047) | 둘 다 작업 행을 먼저 잠근다 → 직렬화. 취소가 먼저 커밋되면 S1 |
| 그룹 검토 ↔ F2 항목 이동 | 둘 다 작업 행(id 오름차순)을 먼저 잠근다 → 직렬화 |
| 그룹 검토 ↔ PCT 적재의 그룹 재구성 | 그룹 테이블을 잠그지 않는다. 함수 시작 시점(②)의 구성으로 처리하고, 응답의 처리 QC번호로 알린다(intent Open questions) |
| 트랜잭션 밖 알림 INSERT 의 FK 공유 잠금과의 순환 | 40P01 이면 `rpcWithDeadlockRetry` 가 한 번 재시도(함수 전체가 롤백되므로 안전) [현행 유지] |

## 6. 그룹 승인 — 원자적이지 않다

| 단계 | 동작 |
|---|---|
| ① | 그룹 존재·오더 2건 이상(§4 A2·A3) |
| ② | 그룹 오더의 작업 전부를 읽는다(QC번호 순) |
| ③ | 작업마다: `승인완료` → skipped `이미 승인완료` / `승인전` 이 아님 → skipped `"{단계}" 단계` / `승인전` → 기존 `advanceJobStage(작업, '승인전', 관리자)` 호출 |
| ④ | `advanceJobStage` 가 거절하면(전 항목 검토 미완료 `모든 시험항목의 검토가 끝나야 승인할 수 있습니다.`, 동시 변경 `이미 "{단계}" 단계로 변경되었습니다…` 등) 그 메시지를 사유로 skipped, 다음 작업으로 계속 |
| ⑤ | 거절 뒤 작업을 다시 읽어 이미 `승인완료` 면(승인 update 는 커밋됐고 후속 동기화·알림에서 실패) processed 로 센다 [구현] |
| ⑥ | 승인 0건이면 §4 A4 거절 |

- 오더 상태 동기화(`syncOrderStatusFromJobs`)·상태 이력(source `manual`)·슬랙·앱 알림은 **`advanceJobStage` 가 작업마다 이미 한다** — 그룹 서비스가 다시 부르지 않는다(중복 호출 금지).
- 각 작업의 승인 조건(`승인전` + 전 항목 `reviewed`)은 느슨해지지 않는다. `expected='승인전'` 을 넘겨 조건부 update 로 한 번만 성공한다.
- **원자 승인이 아니다.** 도중에 서버가 죽거나 DB 오류가 나면 앞 작업만 `승인완료` 로 남는다. 다시 누르면 남은 작업만 처리된다(앞 작업은 `이미 승인완료` skip).
- 반환: `{ groupId, processed: [{jobId, orderId, qcNo, batchNo}], skipped: [{jobId, qcNo, batchNo, reason}] }`

## 7. 경계 사례 판정표 (브리프 §3.4 의 12건)

| # | 상황 | 판정 |
|---|---|---|
| 1 | 3배치 중 1배치의 그 항목이 아직 시험 중 + [그룹 검토 시작] | 2배치만 `reviewing`. 1배치는 skipped `시험이 끝나지 않음`. 이후 단건 또는 그룹 버튼 재클릭(멱등)으로 처리 |
| 2 | 1배치는 이미 `reviewing` | skipped `이미 검토 중`(멱등). 이력·단계 변화 없음 |
| 3 | 1배치 작업이 `승인완료` | skipped `승인완료 작업`. 전체를 거절하지 않는다 |
| 4 | 1배치 작업이 `지연` | 검토 처리, 단계는 `지연` 유지(`recompute_job_stage` 가 `changed=false`) |
| 5 | 1배치에 그 이름의 항목이 없음 | 조용히 건너뜀(skipped 에 넣지 않음) |
| 6 | 병렬 배정으로 한 오더의 작업이 담당자별로 여러 개 | 그 이름의 항목을 가진 작업만 처리. 담당자가 달라도 관리자 동작이라 모두 대상 |
| 7 | 대상 0건(전부 skip) | `처리할 시험항목이 없습니다.` 로 거절, 이력·단계 변화 없음 |
| 8 | 처리 중 F2 항목 이동·작업 시작 취소와 경합 | 작업 행 잠금(id 오름차순)으로 직렬화. 취소가 먼저면 S1 skip, 이동이 먼저면 잠근 뒤 읽은 소속대로 처리. **전체 거절하지 않는다** |
| 9 | [그룹 승인]인데 1배치가 아직 `검토중` | 그 배치 skipped `"검토중" 단계`, 나머지 승인. 오더 상태는 `advanceJobStage` 가 오더마다 동기화 |
| 10 | 작업 시작 뒤 그룹 구성이 바뀜 | 조작 시점 구성으로 다시 계산. 응답의 처리·건너뜀 QC번호로 결과를 보인다 |
| 11 | 알림 | 단계가 실제로 바뀐 작업마다 `notifyStageRecomputed` 1회(검토). 승인은 `advanceJobStage` 의 기존 알림(작업마다 1회). 항목 수만큼 보내지 않는다 |
| 12 | DB 설치 미적용 | 0048 은 운영 적용 완료(해당 없음). **0051 미적용**이면 그룹 검토는 §4 설치 문구로 거절, 비원자 폴백 없음. 그룹 승인은 0051 에 의존하지 않는다 |

## 10. 배포

- 마이그레이션 **`0051_group_stage_progress.sql`**. 0045 헤더 형식, **Supabase 대시보드 > SQL Editor 수동 적용**, idempotent(`create or replace`),
  `supabase db push` 금지, 본문 `begin; … commit;`, 끝에 `notify pgrst, 'reload schema';`.
- 순서: **SQL 0051 적용 → 앱 배포(main push)**. 테이블 구조·데이터 변경이 없어 재실행해도 안전하다.
- 미적용 상태로 앱이 먼저 나가도 단건 검토·승인과 그룹 승인은 영향 없고, 그룹 검토만 설치 문구로 거절된다.

## 11. 범위 밖

- 검토 취소·재실시·관리자 직접 변경의 그룹 전파.
- 원자적 그룹 승인(DB 함수화).
- 시험자 할 일 화면의 그룹 카드 검토 진행 표시.
- 전 배치 검토 완료 시 자동 승인.
- 그룹 구성 변경의 잠금·버전 검사(그룹 테이블 잠금).
- 작업 현황 레인에서 그룹 단위로 카드를 합치는 표시(배지만).

### 11.1 [구현] 세부의 이유

| 무엇 | 정한 것 | 이유 |
|---|---|---|
| 내부 함수 `group_review_apply` | 항목 단위·일괄이 한 본문을 공유 | 배치별 판정·잠금 순서를 두 벌 쓰지 않기 위해 |
| 그룹 버튼 노출 | 그룹의 시작된 작업 2건 이상 | 오더는 2건이어도 작업이 1건뿐이면 그룹 적용이 단건과 같다 |
| 승인 0건 문구 | `승인할 배치가 없습니다.` + 건너뜀 요약 | 결정의 `처리할 시험항목이 없습니다.` 는 검토 문맥 문구라 승인에서는 뜻이 어긋난다. 승인은 트랜잭션이 아니라 사유를 돌려줄 수 있다 |
| 승인 뒤 재조회 | 거절 뒤 이미 승인완료면 processed | `advanceJobStage` 는 승인 update 커밋 뒤 오더 동기화에서 던질 수 있어, 그대로 skip 으로 세면 결과가 사실과 달라진다 |
| 작업 상세 `group` | 관리자 응답에만 | 시험자 열람 권한을 그룹 멤버로 넓히지 않기 위해 |
