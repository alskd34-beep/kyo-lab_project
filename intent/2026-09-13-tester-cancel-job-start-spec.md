# Spec: 시험자 작업 시작 취소 — 상태 전이 규칙
Author: kyo (개발) · Status: completed
관련 intent: [2026-09-13-tester-cancel-job-start.md](./2026-09-13-tester-cancel-job-start.md)
설계 근거: 레드팀 분석(작업 시작 취소 설계, 2026-09-13) · 레드팀 diff 검토(차단 7건, 2026-09-14)

이 문서는 작업 시작 취소가 **언제 허용되고, 무엇이 바뀌며, 무엇이 남는가**를 못박는다.
최종 판정은 서버의 DB 함수 `cancel_job_start`(마이그레이션 0047)가 하며, 화면의 버튼 노출은 같은 규칙의 보조 판정일 뿐이다.

## 1. 전이

| 대상 | 취소 전 | 취소 후 |
|---|---|---|
| 작업(`qc_jobs` 행) | `진행중` | **행 삭제**(원복). 새 상태값 없음 |
| 시험항목 체크리스트(`qc_job_items`) | 전부 `pending`, 실행 흔적 없음 | 작업과 함께 삭제(cascade) |
| 작업 상태 이력(`qc_job_status_history`) | `null → 진행중` 1건 | 작업과 함께 삭제(cascade) — 감사는 §5 로 대체 |
| 오더 상태(`pct_orders.status`) | `진행중` 또는 `지연` | §4 규칙으로 결정 |
| QC번호 | 부여됨 | 작업과 함께 사라짐. **이후 재사용될 수 있음**(감사 기록에 당시 번호를 남기는 이유). 채번은 "같은 분의 최대 시퀀스 + 1" 이라, 중간 번호가 지워져 **반복 충돌하던 문제는 없다**. 같은 순간의 동시 시작 충돌은 기존처럼 UNIQUE 제약과 재시도로 처리한다 |
| LOCK(`locked/locked_by/locked_at`) · 담당자 · 예정 기간 | — | **변경 없음** |
| 오더 시험항목 스냅샷(`pct_order_test_items`) · 동시분석 그룹 · 장비 예약 | — | **변경 없음** |
| 기존 "작업 시작" 알림 · 이미 발송된 슬랙 | — | **변경 없음**(지우지 않음) |
| 관리자 알림의 `related_qc_job_id`(이 작업을 가리키던 것) | 작업 id | FK `on delete set null` 로 비워짐 |

## 2. 허용 조건 — 전부 AND

| # | 조건 | 판정 기준 | 거절 메시지(전문) |
|---|---|---|---|
| 0 | 사유 | 문자열이고 앞뒤 공백 제외 2자 이상 | 문자열 아님/본문 이상: `시작 취소 사유를 입력해 주세요.` · 2자 미만: `시작 취소 사유를 2자 이상 입력해 주세요.` |
| 1a | 작업 존재 | 해당 작업 id 의 행이 있음 | `작업을 찾을 수 없습니다.` |
| 1b | 본인 작업 | `qc_jobs.assignee_user_id` = 로그인 사용자 | `본인 작업만 수정할 수 있습니다.` |
| 2 | 작업 상태 | `qc_jobs.status = '진행중'` (지연·검토전·검토중·승인전·승인완료 모두 거절) | `"{현재 상태}" 상태의 작업은 시작을 취소할 수 없습니다. 시작 취소는 '진행중' 상태이고 시험항목을 하나도 시작하지 않은 작업만 가능합니다.` |
| 5 | 오더 상태 | 오더가 존재하고 `pct_orders.status ≠ '삭제'` | 없음: `오더를 찾을 수 없습니다.` · 삭제: `삭제된 오더의 작업은 시작을 취소할 수 없습니다. 관리자에게 문의하세요.` |
| 4 | 항목 존재 | 해당 작업의 `qc_job_items` 가 **1건 이상** (0건 = 시작 도중의 부분 상태일 수 있음) | `시험항목 체크리스트가 없는 작업은 시작을 취소할 수 없습니다. 관리자에게 확인을 요청하세요.` |
| 3 | 전 항목 미실행 | 모든 항목이 `status='pending'` AND `started_at`·`cleared_at`·`elapsed_minutes`·`elapsed_total_minutes` 모두 NULL | `이미 시작했거나 완료한 시험항목이 있어 작업 시작을 취소할 수 없습니다.` |
| 7 | 검토·전이 이력 없음 (0048 추가) | 그 작업의 `qc_job_item_review_history` 가 0건 AND `qc_job_status_history` 에 작업 시작(`from_status` null) 외의 전이가 0건 — 재실시로 흔적이 비워진 작업의 상태 이력이 cascade 로 사라지지 않게 | `검토·재실시 이력이 있는 작업은 시작을 취소할 수 없습니다. 관리자에게 문의하세요.` |
| 6 | LOCK | **보지 않는다.** LOCK 이어도 허용, LOCK 값은 유지 | (거절 없음) |
| — | 설치 | DB 함수 `cancel_job_start` 가 있음(§7) | `시작 취소 기능의 DB 설치(0047 마이그레이션)가 아직 적용되지 않았습니다. 관리자에게 문의하세요.` |

- 판정 순서: 0 → 1a → 1b → 2 → 5 → 4 → 3 → 7(0048). 앞 조건에서 거절되면 뒤 조건은 보지 않는다.
- 조건 0 은 라우트(본문 형태)·서비스(문자열·2자)가 먼저 보고, 함수도 빈 사유를 한 번 더 막는다.
  조건 1a~3 은 **함수 안에서 행을 잠근 뒤** 판정한다(§4). 함수의 거절은 `errcode P0001` 이고 메시지를 그대로 화면에 보인다.
- 조건 3 은 "과거에 한 번도 시험하지 않았음"이 아니라 **"지금 실행 흔적이 없음"** 이다. 항목 단위 시작 취소는
  흔적을 남기지 않으므로, 항목을 시작했다가 개별 취소한 작업도 허용된다(intent Open questions).
- 화면: 조건 2·3·4 를 같은 기준으로 계산해 충족하는 작업에만 [시작 취소]를 보인다.
  진행 중 섹션의 낱개 작업 카드, 동시분석 그룹 카드의 배치 표시에 각각 붙는다(그룹 전체로 번지지 않음).

## 3. 권한

| 요청자 | 자기 작업 | 병렬 배정 동료의 작업 | 타인 작업 |
|---|---|---|---|
| 시험자(담당자 1 = 대표) | 허용(§2 충족 시) | 거절 | 거절 |
| 시험자(담당자 2~N, 병렬 배정 — 2026-09-15 이후 최대 5명) | 허용(§2 충족 시) | 거절 — 열람 권한을 수정 권한으로 쓰지 않음 | 거절 |
| 관리자 | 자기 작업만 시험자와 같은 규칙 | 거절 | 거절 — 대리 정정은 기존 관리자 상태 변경(사유 필수) 통로. 대리 취소는 범위 밖 |

권한 주체는 요청 본문 값이 아니라 로그인 토큰의 사용자 id 다. 서버가 토큰에서 꺼낸 id 를 함수의 `p_user_id` 로 넘긴다.

### 3.1 함수 실행 권한 — service_role 만

`cancel_job_start(p_job_id, p_user_id, p_reason)` 는 `p_user_id` 를 **그대로 믿는다**. anon 키를 가진 누구나
PostgREST 로 이 함수를 부를 수 있다면 남의 작업을 지울 수 있다. 그래서:

| 역할 | 실행 권한 |
|---|---|
| `public` · `anon` · `authenticated` | **revoke** |
| `service_role`(서버의 관리자 클라이언트) | **grant execute** |

## 4. 처리 순서와 경합 — 함수 한 트랜잭션

서비스는 사유 검사 → 함수 호출 → 오류 번역 → (커밋 뒤) 알림만 한다. 아래 ①~⑦은 **함수 본문 전체가 한 트랜잭션**이며,
어느 단계에서 실패하든 **전부 롤백**된다(감사 기록만 남거나, 취소는 됐는데 감사 기록이 없는 상태가 생기지 않는다).

| 단계 | 동작 | 실패 시 |
|---|---|---|
| ① | 작업 행 잠금(`qc_jobs … for update`) → 조건 1a·1b·2 | 거절 메시지, 전부 롤백 |
| ② | 오더 행 잠금(`pct_orders … for update`) → 조건 5 | 거절 메시지, 전부 롤백 |
| ③ | 그 작업의 시험항목 행 전부 잠금(`qc_job_items … for update`) → 조건 4·3·7(0048 이 함수를 재정의해 추가) | 거절 메시지, 전부 롤백 |
| ④ | 감사 기록 `jobStart` 행 insert(§5) | DB 오류 그대로, 전부 롤백 |
| ⑤ | 작업 삭제(항목·작업 상태 이력은 cascade) | DB 오류 그대로, 전부 롤백 |
| ⑥ | 오더 상태 결정(아래) + 실제로 바뀐 경우 `status` 감사 행 insert | DB 오류 그대로, 전부 롤백 |
| ⑦ | 결과 반환: `qcNo`·`orderId`·`productName`·`batchNo`·`orderStatusBefore`·`orderStatusAfter` | — |
| (커밋 뒤) | 관리자 알림 1건(§6) | 취소 성공은 유지하고 응답에 경고: `작업 시작은 취소됐지만 관리자 알림 생성에 실패했습니다.` |

**잠금 순서는 작업 → 오더 → 항목으로 고정한다**(교착 방지).

**동시 요청**
- **동시 항목 시작·완료**: 항목 쓰기는 ③의 행 잠금을 기다린다. 취소가 커밋되면 그 행은 이미 없으므로 **대기 후 0행 갱신**이 된다
  (아무 실적도 저장되지 않았고, 따라서 지워진 실적도 없다). 반대로 항목 쓰기가 먼저 커밋됐다면 ③ 뒤의 조건 3 검사가 그것을 보고
  거절한다. **어느 순서든 기록된 실적이 삭제되는 경우는 없다.**
- **두 번 누른 취소**: 두 번째 요청은 ①에서 첫 요청의 커밋을 기다린 뒤 행이 없으므로 `작업을 찾을 수 없습니다.` 로 거절된다.
  감사 기록·알림이 중복되지 않는다.
- **늦게 도착한 이전 취소 요청**: 같은 오더를 다시 시작하면 **새 작업 id** 가 생기므로 이전 요청이 새 작업을 지우지 않는다.
- **병렬 배정 동료의 시작·오더 삭제**: 오더 행을 ②에서 잠그므로 오더 상태 판단(⑥)과 쓰기 사이에 다른 요청이 끼어들 수 없다.
  남은 작업이 있으면 오더를 쓰지 않는다(아래). 서비스는 커밋 뒤에 작업 기준 오더 동기화를 **추가로 부르지 않는다**(경합을 다시 열지 않기 위해).
- **응답 유실**: 서버는 취소했는데 화면이 응답을 못 받으면, 화면은 오류를 보여 준 뒤 목록을 한 번 다시 읽는다.
  대상 작업이 목록에 없으면 확인 창을 닫고 `목록을 새로 불러왔습니다. 작업이 이미 취소됐는지 확인해 주세요.` 를 띄운다.

**되돌린 뒤의 오더 상태(⑥)**

| 그 오더에 남은 작업(⑤ 뒤, 잠금 아래) | 오더 상태 | 쓰기 |
|---|---|---|
| 0건, 오더가 `대기` 아님 | `대기` | `pct_orders.status='대기'` + `status` 감사 행 |
| 0건, 오더가 이미 `대기` | `대기`(그대로) | 없음 |
| 1건 이상(병렬 배정 동료 작업 — 1건이든 N−1건이든) | **취소 전 값 그대로** | 없음 |

남은 작업이 1건 이상일 때 오더를 건드리지 않아도 되는 이유(증명 — 담당자 수와 무관하다. 병렬 배정(N명, 최대 5명)에 그대로 성립):
- 취소 대상은 `진행중` + 실행 흔적 0 인 작업, 즉 이 오더에서 **가장 덜 진행된 작업**이다.
- 취소 전 오더 = (다른 작업 중 하나라도 `지연`이면 `지연`, 아니면 최소 단계 = 내 작업의 `진행중`).
- 취소 후 재산정 = 내 담당 슬롯이 미시작으로 돌아가 "활성 항목이 있는 미시작 담당자가 한 명이라도 남으면 `진행중` 상한" 이 걸린다
  → (다른 작업 중 하나라도 `지연`이면 `지연`, 아니면 `진행중`). 다른 작업이 몇 건이든 같다.
- 두 값이 **같다.** 그러므로 `orderStatusAfter = orderStatusBefore` 이고 쓸 것이 없다.

> 한계(메모): 시작 이후 오더 시험항목 스냅샷이 바뀌어 내 슬롯의 활성 항목이 0건이 되면 위 상한이 걸리지 않는다.
> 이 경우에도 함수는 오더를 건드리지 않으며, 다음 작업 전이(항목 완료·단계 변경) 때 기존 오더 동기화가 바로잡는다.

**알려진 한계(메모 — 이번 범위 밖, 3차 레드팀)**
- **항목 쓰기의 거짓 성공**: 위 "대기 후 0행 갱신" 에서 기존 항목 시작·완료 API 는 갱신 행 수를 보지 않아
  화면에 저장 성공을 알릴 수 있다. 실적이 지워지는 것은 아니며(애초에 저장되지 않음), 목록 새로고침 때 작업이 사라져 드러난다.
  갱신 행 확인은 항목 API 쪽 별도 변경으로 다룬다.
- **오더 물리 삭제와의 교착**: 시트 적재가 수동 오더를 물리 삭제하는 경로(오더 → 작업 cascade)는 이 함수(작업 → 오더)와
  잠금 순서가 반대다. 같은 순간에 겹치면 Postgres 가 교착을 탐지해 **한쪽을 롤백**한다 — 데이터가 반쯤 바뀌는 일은 없고,
  취소 쪽이 롤백되면 시험자는 일반 DB 오류를 보고 다시 시도하면 된다.
- **DB 오류 문구**: 표의 "DB 오류 그대로" 는 서버 내부 전파를 뜻한다. 화면에 보이는 문구는 라우트가 정하며,
  `Error` 가 아닌 오류 객체는 `서버 오류` 로 보인다.

## 5. 감사 기록

`qc_job_status_history` 는 작업 삭제와 함께 cascade 로 사라지므로 쓰지 않는다. 오더에 붙는 `pct_order_edits` 에 **사실만** 남긴다.

**항상 1행 — 작업 시작 취소 사건**

| 컬럼 | 값 |
|---|---|
| `order_id` | 해당 오더 |
| `field` | `jobStart` (오더 화면 수정 이력에 "작업 시작" 으로 표시) |
| `old_value` | `QC {QC번호} · 진행중` — **QC번호를 반드시 포함**(번호 재사용 대비) |
| `new_value` | `시작 취소` |
| `reason` | `{사용자가 고른 사유}` |
| `edited_by` | 요청한 로그인 사용자 |
| `edited_at` | 서버 기본값(now) |

**오더 상태가 실제로 바뀐 경우에만 1행 더**(§4 표의 첫 줄)

| 컬럼 | 값 |
|---|---|
| `field` | `status` |
| `old_value` | 취소 전 오더 상태(잠금 아래에서 읽은 실제 값) |
| `new_value` | `대기` |
| `reason` | `작업 시작 취소 (QC {QC번호})` |
| `edited_by` | 요청한 로그인 사용자 |

- 두 행과 작업 삭제·오더 상태 쓰기는 한 트랜잭션이다. 취소가 일어나지 않았으면 기록도 없고, 기록이 실패하면 취소도 없다.
- 병렬 배정으로 오더 상태가 유지된 취소에는 `status` 행이 **없다**(일어나지 않은 `진행중 → 대기` 를 적지 않는다).

## 6. 알림

| 항목 | 값 |
|---|---|
| 대상 | 관리자 공지(대상 사용자 없음) · 앱 내 |
| type / severity | `status_changed` / `warning` |
| title | `작업 시작 취소` |
| body | `{품목명} / {제조번호} — QC {QC번호} 작업 시작이 취소되었습니다. (사유: {사유})` |
| 관련 작업 | 비움(작업 행이 이미 삭제됨) · 관련 오더는 채움 |

- 알림은 취소 트랜잭션이 **커밋된 뒤** 만든다. 실패해도 취소는 되돌리지 않고, 응답의 `warning` 으로 시험자에게 알린다.
- 알림 재처리 큐는 없다(범위 밖 — 실패 시 서버 로그와 화면 경고만 남는다).
- 기존 "작업 시작" 알림은 지우지 않는다. 슬랙 정정 메시지는 보내지 않는다.

## 7. 배포

- 이 기능은 마이그레이션 **`0047_cancel_job_start.sql`**(함수 추가 + 실행 권한 설정. 테이블 구조·기존 데이터 변경 없음)이 있어야 동작한다.
- **Supabase 대시보드 > SQL Editor 에서 수동 적용**한다(idempotent). `supabase db push` 는 쓰지 않는다.
- 미적용 상태에서 [시작 취소] 를 누르면 §2 "설치" 행의 메시지로 거절된다. 서버는 **여러 호출로 나눈 비원자 방식으로 대신 처리하지 않는다**
  (그 방식은 §4 의 실적 삭제 경합과 감사 부분 실패를 되살린다).
- 함수 안의 상태 문자열(`진행중`·`대기`·`삭제`·`pending`)은 `types/qc-status.ts` 와 같은 값이어야 한다. 그 파일을 바꾸면 함수도 함께 바꾼다.

## 8. 화면

| 선택지 | 서버로 보내는 사유 |
|---|---|
| 잘못 눌렀습니다 | `잘못 눌렀습니다` |
| 시험 준비가 안 됐습니다 | `시험 준비가 안 됐습니다` |
| 기타 | 직접 입력한 문구(2자 이상이어야 [시작 취소] 활성) |

- 확인 창 본문·버튼 설명: "내 작업 기록과 QC번호가 삭제됩니다. 다른 담당자 작업이 없으면 오더가 시작 대기로 돌아갑니다."
- 성공 문구는 응답의 `orderStatusAfter` 로 가른다.

| `orderStatusAfter` | 문구 |
|---|---|
| `대기` | `QC {QC번호} 작업 시작을 취소했습니다. 오더가 시작 대기로 돌아갔습니다.` |
| 그 외 | `QC {QC번호} 내 작업 시작을 취소했습니다. 함께 배정된 담당자의 작업이 있어 오더는 '{상태}'로 유지됩니다.` |

- 응답에 `warning` 이 있으면 위 문구 뒤에 경고를 붙여 오류 색으로 보인다.
- 거절되면 확인 창을 닫지 않고 서버 메시지를 그대로 보여 주며, 목록을 한 번 다시 읽는다(§4 응답 유실).
