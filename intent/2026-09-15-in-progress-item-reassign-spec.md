# Spec: 진행 중 시험항목 담당자 변경 — 이동 규칙
Author: kyo (개발) · Status: completed
관련 intent: [2026-09-15-in-progress-item-reassign.md](./2026-09-15-in-progress-item-reassign.md)
근거: 감독 결정 `temp/decisions-f1-f2-f3.md`(F2·공통·**보강 결정 F2-1~F2-8** — 단일 기준) · 탐색 브리프 `temp/brief-f2-item-reassign.md`

이 문서는 진행 중인 오더에서 시험항목 하나를 다른 담당자에게 넘기는 일이 **언제 허용되고, 무엇이 바뀌며, 무엇이 기록되는가**를 못박는다.
최종 판정은 DB 함수 `reassign_job_item`(마이그레이션 0050)이 하며, 화면의 버튼 노출·비활성은 같은 규칙의 보조 판정일 뿐이다.

표기
- 무표시 = 결정 문서에 있는 규칙.
- **[브리프 준용]** = 결정 문서가 정하지 않았고, 브리프 권고가 결정과 충돌하지 않아 그대로 옮긴 세부.
- **[현행 유지]** = 지금 코드의 규칙·문구를 그대로 이어 쓰는 것.
- **[구현]** = 구현하면서 정한 세부(§12.1 에 이유).

## 0. 의존 — 이 기능은 단독으로 동작하지 않는다

| 의존 대상 | 출처 | 이 기능에서 쓰는 곳 |
|---|---|---|
| 단계 재도출 SQL 함수 `recompute_job_stage(p_job_id, p_actor, p_note)` | [시험항목 단위 검토 spec](./2026-09-15-item-level-review-spec.md) §2·§5.3, 마이그레이션 0048 | 이동 트랜잭션 안에서 보내는 쪽(A)·받는 쪽(B) 작업 단계 재도출 |
| `qc_job_items.review_status` 등 검토 컬럼, 검토 이력 FK `on delete set null` | 같은 spec §1.1·F1-1, 0048 | "검토 흔적 0" 판정, 행 삭제 뒤에도 검토 이력 보존(F2-4) |
| `ITEM_EDITABLE_JOB_STATUSES = {진행중, 지연, 검토전, 검토중}` | 같은 spec §3.4 | 보내는 쪽·받는 쪽 작업 상태 판정, 시험자 버튼 노출 |
| 담당자 테이블 `pct_order_assignees(order_id, slot, tester_id)` | [병렬 배정 spec](./2026-09-15-parallel-assignment-spec.md) §1.1, 마이그레이션 0049 | "같은 그룹" 판정, 보내는·받는 슬롯 |
| 항목 슬롯 제약 `between 1 and 5` | 같은 spec §1.2, 0049 | 스냅샷 슬롯 갱신 |

- 0050 은 파일 첫머리에서 두 의존(`recompute_job_stage` 함수·`pct_order_assignees` 테이블·`qc_job_items.review_status` 컬럼)이 있는지 확인하고,
  없으면 `0048_item_review.sql·0049_parallel_assignment.sql 을 먼저 적용하세요.` 로 **적용 자체를 중단**한다(파일 전체 `begin … commit`).

## 1. 데이터 모델

- **테이블·컬럼 변경 없음.** 새 상태값(`transferred` 등)도 만들지 않는다 — 흔적 없는 행만 옮기므로 필요 없다.
- 인덱스 [브리프 준용]: `idx_qc_job_items_job_name` = `qc_job_items(qc_job_id, test_item_name)` — 이름 매칭 조회용.
- 신규 DB 함수 `reassign_job_item` 1개(§5).

## 2. 규칙

### 2.1 "같은 그룹"

| 항목 | 규칙 |
|---|---|
| 정의 | **그 오더의 `pct_order_assignees` 행 전체**(병렬 배정 담당자 집합) |
| 식별 | 보내는 쪽 A·받는 쪽 B 는 **슬롯 번호**로 식별한다(F2-1·F2-7). 받는 슬롯은 그 오더에 존재해야 한다 |
| 판정 위치 | SQL 함수가 같은 테이블로 최종 판정. 화면 조회(서비스 `getItemReassignContext`)는 `isOrderCoAssignee` 와 같은 기준(행 ≥ 2 이고 조회자가 슬롯에 있음)으로 시험자의 열람을 막는다 |
| 조직 팀·파트 | 도입하지 않는다(intent Open questions) |
| 1인 배정 오더 | 받는 슬롯이 없음 → 버튼 숨김(할 일)·서버 거절(조건 3a) |

### 2.2 옮길 수 있는 항목 — 전부 AND

| # | 조건 |
|---|---|
| 1 | 스냅샷 행(`pct_order_test_items`)이 있고 **제외(`is_excluded`)가 아니다**(F2-2) |
| 2 | 스냅샷 슬롯 = 요청의 기대 슬롯(F2-7) |
| 3 | A 에게 작업이 있으면: 그 작업에 그 항목 행이 정확히 1건, `status = 'pending'`, `started_at`·`cleared_at`·`elapsed_minutes`·`elapsed_total_minutes` 모두 null(0047 의 "실행 흔적 0"), `review_status = 'none'` |
| 4 | A 에게 작업이 없으면: 이 오더의 어떤 작업에도 그 이름의 행이 없다 |

- `in_progress`·`cleared` 는 거절(먼저 A 가 항목 시작 취소).
- 재실시로 흔적이 비워진 항목(검토 이력은 있음)은 조건상 이동 가능하다. 행이 삭제돼도 검토 이력은 FK `set null` + 스냅샷 컬럼으로 남는다(F2-4).

### 2.3 이동 방식 — 네 경우(F2-1)

"작업 有" = 그 슬롯 담당자의 이 오더 `qc_jobs` 행이 있음.

| A 작업 | B 작업 | 동작 | 반환 `mode` |
|---|---|---|---|
| 有 | 有 (`진행중`·`지연`·`검토전`·`검토중`) | 항목 행의 `qc_job_id` 를 B 작업으로 **UPDATE**(행 id·`sequence_order` 유지 [브리프 준용]) | `moved` |
| 有 | 無 | A 작업에서 그 항목 행 **삭제**(흔적 0 행만). B 작업은 **자동 생성하지 않는다**(B 가 [작업 시작] 할 때 스냅샷으로 포함) | `released` |
| 無 | 有 (`진행중`·`지연`·`검토전`·`검토중`) | B 작업에 **pending 행 추가**(`test_item_id`·`test_item_name`·`sequence_order` 는 스냅샷 값) | `attached` |
| 無 | 無 | 스냅샷만 변경 | `snapshot` |
| — | 有 (`승인전`·`승인완료`) | **거절** | — |

- 네 경우 모두 스냅샷 `pct_order_test_items.assignee_slot` 을 B 슬롯으로 바꾼다 — 스냅샷과 실제 체크리스트는 같은 트랜잭션에서 함께 바뀐다
  (오더 상태·시작 대기 목록·월간 스케줄이 스냅샷을 읽는다).
- A 작업에 남는 항목이 **0건**이 되는 이동은 거절한다(A 작업이 있을 때).
- **오더에 작업이 1건도 없으면** 이 경로를 쓰지 않는다 — 작업 시작 전 배분은 오더 수정 서랍의 일괄 배분(`set_order_test_item_slot`)이 맡는다(F3-7) [구현].

### 2.4 상태 재동기화

| 대상 | 시점 | 동작 |
|---|---|---|
| A 작업(있을 때) | 이동 트랜잭션 안 | `recompute_job_stage(A, p_user_id, note)` — 예: 남은 항목이 전부 완료면 `진행중 → 검토전` |
| B 작업(있을 때) | 이동 트랜잭션 안 | `recompute_job_stage(B, p_user_id, note)` — 예: `검토전` 에 pending 항목이 붙으면 `검토전 → 진행중`, `검토중` 은 그대로 |
| 오더 | **커밋 뒤** | 단계가 바뀐 작업이 있으면 F1 `notifyStageRecomputed`(오더 동기화 포함), 없어도 `syncOrderStatusFromJobs(orderId)` 를 **항상** 한 번 — B 가 미시작이면 B 슬롯에 활성 항목이 생겨 `진행중` 상한이 걸릴 수 있다 |

- note: `시험항목 "{항목명}" 담당자 변경으로 서버가 자동 전환했습니다.`(F1 spec §6.2 형식)
- `지연`·`승인완료` 작업은 재도출되지 않는다(F1 규칙).

### 2.5 경계 사례 판정표

| # | 상황 | 판정 |
|---|---|---|
| E1 | 항목 흔적 0, B 작업 `진행중` | 행 이동 + 스냅샷 B + 감사 (`moved`) |
| E2 | 항목 흔적 0, B 작업 없음 | A 에서 행 삭제 + 스냅샷 B + 감사 (`released`). B 시작 대기 목록에 나타남 |
| E2' | A 작업 없음(미시작 담당자 몫), B 작업 `진행중` | B 작업에 pending 행 추가 + 스냅샷 B + 감사 (`attached`) |
| E2'' | A·B 모두 작업 없음(오더에는 다른 담당자 작업이 있음) | 스냅샷만 B + 감사 (`snapshot`) |
| E3 | 항목 `in_progress` | 거절 |
| E4 | 항목 `cleared`(검토 여부 무관) | 거절 |
| E5 | `status=pending` 인데 시각·소요 값이 남은 비정상 행 | 거절 |
| E6 | B 작업 `승인전`·`승인완료` | 거절 |
| E7 | B 작업 `지연`·`검토전`·`검토중` | 허용. `검토전` B 는 재도출로 `진행중`, `지연` B 는 그대로 |
| E8 | A 작업이 `승인전`·`승인완료` | 거절(정상 데이터라면 pending 항목이 없음 — 방어) |
| E9 | 옮기면 A 항목 0건 | 거절 |
| E10 | 옮기면 A 의 남은 항목이 전부 `cleared` | 허용. A 재도출(검토 흔적 없으면 `검토전`, 있으면 `검토중`) |
| E11 | 받는 슬롯이 그 오더에 없음(그룹 밖) | 거절 |
| E12 | 받는 슬롯 = 보내는 슬롯 | 거절 |
| E13 | B 비활성 시험자 | 거절 [브리프 준용] |
| E14 | 요청자가 시험자인데 보내는 슬롯의 담당자가 아님(B 의 가져오기 포함) | 거절 |
| E15 | 오더 LOCK | **허용**. LOCK 값·담당자 구성·일정 변경 없음 |
| E16 | 오더 `삭제`·`승인완료` 상태 | 거절 [브리프 준용 + 구현] |
| E17 | 동시분석 그룹 소속 오더 | 허용. 그룹 일괄 조작은 항목명 매칭이라 받는 쪽에서 자동으로 따라감. **할 일의 동시분석 그룹 카드 항목 행에는 [넘기기]를 두지 않는다** — 배치별 기록이라 그룹 단위 이동은 범위 밖(낱개 카드에서만) |
| E18 | B 작업에 같은 이름 항목이 이미 있음(과거 불일치 데이터) | 거절 [브리프 준용] |
| E19 | 1인 배정 오더 | 대상 없음 → 버튼 숨김, 서버 거절(E11) |
| E20 | 스냅샷 행 없음 | 거절 [브리프 준용] |
| E21 | 같은 이름 항목이 A·B 밖의 작업에 있거나 A 작업에 2건 이상 | 거절 [브리프 준용: E18 의 확장] |
| E22 | 이동 직후 A 가 옛 화면에서 그 항목 [시작]·[시작 취소]·[완료](개별·그룹) | 개별 경로: 항목이 그 작업에 없음·이미 완료·조건부 update 0행 모두 `작업 상태가 바뀌었습니다. 새로고침 후 다시 확인해 주세요.` 로 실패 응답(F2-6·리뷰 L2). 그룹 경로: 그 배치만 건너뛰고 `skipped` 로 알림(리뷰 M3) |
| E23 | B 가 받은 뒤 B 작업 시작 취소(0047) | B 작업·항목 삭제, 스냅샷은 B 유지 → 재시작 시 다시 포함 |
| E24 | A 담당자 자체를 C 로 교체(전원 인계) | 범위 밖 |
| E25 | 재실시로 흔적이 사라졌지만 검토 이력이 있는 항목 | 이동 가능. 행 삭제(E2) 시에도 검토 이력은 남는다(F2-4). **알려진 비대칭(리뷰 L7)**: 검토 이력의 `qc_job_id` 가 A 작업으로 남아, 항목이 떠난 뒤에도 **A 의 작업 시작 취소는 계속 거절**되고(0048 조건 7), 받은 B 는 그 항목을 가진 채 시작을 취소할 수 있다(행 삭제·이력 FK set null). GMP 기록은 양쪽 모두 보존되며 결정대로 둔다 |
| E26 | 스냅샷 행이 `is_excluded=true` | 거절 — A 작업에 행이 남아 있어도(F2-2) |
| E27 | 스냅샷 슬롯이 기대 슬롯과 다름(다른 관리자가 먼저 옮김) | 거절(F2-7) |
| E28 | A 작업은 있는데 그 체크리스트에 항목이 없음(시작 뒤 추가된 항목 등 이미 어긋난 데이터) | 거절 [구현] |
| E29 | 오더에 작업이 1건도 없음 | 거절 — 일괄 배분을 쓴다(F3-7) [구현] |

## 3. 허용 조건과 거절 메시지(전문)

판정 순서는 아래 표의 번호 순이다. 앞에서 거절되면 뒤는 보지 않는다.
함수의 거절은 `errcode P0001`, 서비스가 메시지를 그대로 보인다. 잠금 위치는 §5.2.

| # | 조건 | 거절 메시지(전문) |
|---|---|---|
| 0a | 사유: 문자열, 앞뒤 공백 제외 **2자 이상** | 없음/문자열 아님: `담당자 변경 사유를 입력해 주세요.` · 2자 미만: `담당자 변경 사유를 2자 이상 입력해 주세요.` |
| 0b | 항목명 있음 | `시험항목을 찾을 수 없습니다.` |
| 0c | 두 슬롯 1~5 | `담당자 번호는 1~5 사이여야 합니다.` |
| 0d | 보내는 슬롯 ≠ 받는 슬롯 | `현재 담당자와 같은 사람에게는 넘길 수 없습니다.` |
| 1 | 요청자가 활성 사용자(users 재확인) | `로그인 사용자를 확인할 수 없습니다. 다시 로그인해 주세요.` |
| 2 | 오더 존재, `status ∉ {삭제, 승인완료}` | 없음: `오더를 찾을 수 없습니다.` · 삭제: `삭제된 오더의 시험항목은 담당자를 변경할 수 없습니다.` · 승인완료: `승인완료된 오더의 시험항목은 담당자를 변경할 수 없습니다.` |
| 3a | 받는 슬롯이 그 오더의 `pct_order_assignees` 에 있음 | `같은 오더에 병렬 배정된 담당자에게만 넘길 수 있습니다.` |
| 3b | 보내는 슬롯이 그 오더에 있음 | `그 사이 담당자가 바뀌었습니다. 새로고침 후 다시 확인해 주세요.` |
| 3c | 요청자 = 관리자, 또는 users.tester_id = 보내는 슬롯의 시험자 | `본인 시험항목만 넘길 수 있습니다.` |
| 3d | B 활성 시험자 | `비활성 시험자({이름})에게는 배정할 수 없습니다.` [현행 유지] |
| 4 | 잠금 전 읽은 두 슬롯의 담당자·작업이 잠금 뒤와 같음 | `다른 사용자가 먼저 변경했습니다. 새로고침 후 다시 시도하세요.` [현행 유지 문구] |

## 5. 처리 순서와 경합

### 5.1 RPC 시그니처 (F2-7)

`reassign_job_item(p_order_id uuid, p_test_item_name text, p_expected_from_slot int, p_to_slot int, p_user_id uuid, p_reason text) returns jsonb`

반환: `orderId`·`productName`·`batchNo`·`testItemName`·`mode`(§2.3)·
`from`(`slot`·`testerId`·`testerName`·`jobId`·`qcNo` — 작업 없으면 null)·
`to`(`slot`·`testerId`·`testerName`·`jobId`·`qcNo`·`userId` — 알림 대상 계정)·
`stages`(`from`·`to` 각각 `recompute_job_stage` 반환값 또는 null).

서비스(`backend/services/jobItemReassign.ts`)는 **사유 검사 → rpc → 오류 번역 → (커밋 뒤) 오더 동기화·단계 전환 알림·받는 사람 알림**만 한다.
함수가 없으면 §3 설치 문구로 거절하고 **비원자 폴백을 하지 않는다**.

### 5.3 잠금 순서 — 근거

**`qc_jobs`(id 오름차순) → `pct_orders` → `pct_order_assignees`(share) → `pct_order_test_items` → `qc_job_items`**

기존 함수들이 잡는 순서를 모두 만족하는 **하나의 전역 순서** `qc_jobs < pct_orders < pct_order_assignees < pct_order_test_items < qc_job_items` 를 따른다.

| 기존 함수 | 잠금 순서 | 전역 순서와 |
|---|---|---|
| 0047/0048 `cancel_job_start` | `qc_jobs → pct_orders → qc_job_items` | 일치 |
| 0048 `recompute_job_stage`·`item_review_action`·`item_review_bulk_action` | `qc_jobs → qc_job_items` | 일치 |
| 0049 `set_order_assignees`·`set_order_primary_assignee`·`set_order_test_item_slot` | `pct_orders → pct_order_assignees → pct_order_test_items` (`qc_jobs` 는 읽기만) | 일치 |
| TS 항목 update, 오더 상태 동기화, 작업 상태 변경 | 문장 하나(자동 커밋)·행 하나(NKU) | 순환 불가 |
| TS `notifications` insert(항목 완료·단계 전환·작업 시작 알림 등) | 문장 하나지만 **FK 검사로 `pct_orders` → `qc_jobs` 순서의 key share** 를 건다 | **역방향 — 순환 가능**(아래) |
| TS `qc_job_status_history` insert | FK 검사 `qc_jobs` → `pct_orders` key share | 같은 방향, 순환 불가 |

- 오더를 먼저 잠그는 0049 방식을 이 함수에 그대로 쓰면 `pct_orders → qc_jobs` 가 되어 0047 과 **역방향**이다
  (0047 이 작업을 잡고 오더를 기다리는 동안 이 함수가 오더를 잡고 작업을 기다리면 교착). 그래서 작업을 가장 먼저 잡는다.
- 어떤 작업을 잡을지는 잠그기 전에 읽은 값으로 정한다. 오더·담당자 행을 잠근 뒤 다시 읽어 **그 사이 담당자·작업 구성이 바뀌었으면 거절**한다(조건 4).
  잠금 뒤에 새로 생긴 작업을 추가로 잠그면 `pct_orders → qc_jobs` 순서가 생기므로 잠그지 않고 거절한다.
- `recompute_job_stage` 는 ⑪에서 이미 잡은 작업 행을 재진입하고 항목 행(전역 순서의 마지막)만 새로 잡는다.
- FK 검사 잠금(항목 이동·추가가 B 작업 행에 거는 key share, 감사 insert 가 오더 행에 거는 key share)은 이미 같은 트랜잭션이 쥔 행이다.
- **작성 당시의 "TS 쓰기는 단일 문장이라 순환이 없다" 는 틀렸다**(리뷰 M1). 단일 INSERT 도 FK 검사로 부모 행 여러 개를 공유 잠금한다.
  이 함수가 작업 행을 쥔 채 오더 행을 기다리는 동안, 같은 작업·오더를 가리키는 알림 insert 가 오더에 key share 를 받고 작업을 기다리면 순환한다
  (0047 `cancel_job_start` 도 같은 구조). 같은 이름 항목이 제3 작업에 있는 이상 데이터에서는 그 작업의 검토·재도출과도 순환할 수 있다(리뷰 L1).
  Postgres 가 한쪽을 40P01 로 중단한다 — 이 함수는 통째로 롤백되므로 서버가 **한 번 재시도**하고(`backend/lib/rpcRetry.ts`, 0047·0048·0049·0050 쓰기 RPC 공통),
  그래도 실패하면 `다른 작업과 동시에 처리되어 저장하지 못했습니다. 잠시 후 다시 시도해 주세요.` 로 안내한다.
  알림 쪽이 중단되는 경우에 대비해 항목 완료(`clearItem`)는 완료 커밋 → 단계 재도출 → 알림 순서로 하고, 알림 실패는 로그만 남기고 성공 응답을 유지한다.

### 5.4 동시 요청

| 경합 | 결과 |
|---|---|
| A 가 같은 항목 [시작]·[완료] ↔ 이동 | 함수가 ⑧에서 항목 행을 잠근다. 시작이 먼저 커밋되면 조건 8d 로 거절. 이동이 먼저 커밋되면 시작·완료 update 는 조건부(`qc_job_id`·`status`)라 0행 → `작업 상태가 바뀌었습니다. 새로고침 후 다시 확인해 주세요.` 로 실패 응답(F2-6) |
| 동시분석 그룹 일괄 [시작]·[완료]·[시작 취소] ↔ 이동 | 그룹 경로는 대상 행마다 개별 함수를 부르고, 그 사이 상태가 바뀐(0행·넘어감) 배치는 **건너뛰고 나머지를 계속** 처리한다. 응답 `affected`(처리)·`skipped`(건너뜀), 화면 `N개 배치 처리, M개는 이미 상태가 바뀌어 건너뛰었습니다.` 후 목록 재조회. 권한·DB 오류는 기존처럼 실패(리뷰 M3) |
| 알림 insert ↔ 이동 | 교착 가능 → 한 번 재시도(§5.3) |
| 관리자 직접 단계 변경(F1-7) ↔ 이동 | 판정~조건부 update 사이에 이동이 B 에 대기 항목을 붙이면(B 가 `지연` 이라 재도출 생략 등) B 가 "검토전 + 대기 항목" 으로 남을 수 있다. 다음 항목 이벤트에서 수렴(F1-7 이 받아들인 범위) |
| A 의 작업 시작 취소(0047) ↔ 이동 | 둘 다 A 작업을 먼저 잠가 직렬화. 취소가 먼저면 조건 4(작업 사라짐)로 거절 |
| 관리자 항목 검토(F1) ↔ 이동 | 작업 행 잠금으로 직렬화. 검토는 `cleared` 항목만 다뤄 대상이 겹치지 않는다 |
| 담당자 구성 변경(F3) ↔ 이동 | `pct_orders` 잠금으로 직렬화. B 가 먼저 빠지면 조건 3a, 보내는 슬롯의 사람이 바뀌면 조건 4 로 거절 |
| 일괄 배분(F3 `set_order_test_item_slot`) ↔ 이동 | 같은 `pct_orders → … → pct_order_test_items` 순서. 일괄 배분은 작업이 있으면 거절, 이 함수는 작업이 없으면 거절 |
| 두 요청이 같은 항목을 다른 사람에게 | 둘째는 ③/④/⑦에서 대기 후 재판정. 스냅샷 슬롯이 기대 슬롯과 달라져 조건 7c 로 거절(F2-7) — **나중 요청이 덮어쓰지 않는다** |
| 담당자의 [작업 시작] ↔ 이동 | **F2-5 — startJob 사후 조정으로 누락·중복을 수렴.** 작업 시작은 오더 행을 잠그지 않고 계획(스냅샷)을 먼저 읽는다(RPC 화는 범위 밖). 이동이 계획 읽기와 작업 행 insert 사이에 커밋되면(이 함수의 오더 잠금이 insert 를 커밋 뒤까지 붙잡으므로 겹치면 반드시) 낡은 계획이 적용돼 **누락**(released: A 에서 지워졌는데 B 의 계획에 없음) 또는 **중복**(attached: B 에 붙었는데 A 의 계획에도 있음)이 생긴다. 그래서 `startJob` 은 병렬 배정 체크리스트 insert 직후 스냅샷을 다시 읽어 맞춘다 — 내 슬롯인데 내 작업에 없는 활성 항목은 대기 항목으로 추가(다른 작업에 같은 이름이 있으면 추가하지 않고 서버 로그 경고), 내 작업에 있는데 스냅샷상 내 몫이 아닌 항목은 **실행 흔적 0·검토 흔적 0 일 때만** 조건부 삭제(흔적이 있으면 지우지 않고 경고). 조정은 멱등. **남는 창**: 조정 자체도 트랜잭션이 아니어서 ① 조정이 스냅샷을 읽은 뒤 쓰기 전에 커밋되는 또 다른 이동, ② 조정 전에 시험자가 넘어간 항목을 시작해 흔적이 생긴 경우(지우지 않고 경고만)는 수렴하지 않는다. 둘 다 사람이 수 초 안에 겹쳐야 하는 경합이며, 조정 실패는 작업 시작을 되돌리지 않고 서버 로그만 남긴다 |

| 컬럼 | 값 |
|---|---|
| `order_id` | 해당 오더 |
| `field` | `testItemAssignee` (수정 이력 화면 라벨 "항목 담당자" [현행 유지]) |
| `old_value` | A 작업 있음: `{항목명}: {A 이름}(QC {A QC번호})` · 없음: `{항목명}: {A 이름}(미시작)` |
| `new_value` | B 작업 있음: `{항목명}: {B 이름}(QC {B QC번호})` · 없음: `{항목명}: {B 이름}(미시작)` |
| `reason` | 사용자 사유(2자 이상, 선택지 문구 또는 직접 입력) |
| `edited_by` | 요청한 로그인 사용자 |
| `edited_at` | 서버 기본값 |

- 이름은 `testers.name` 을 기록 시점에 문자열로 남긴다.
- `reassignment_history`(오더 담당자 재배정 통계)에는 **넣지 않는다**.
- 작업 단계가 바뀐 경우 `qc_job_status_history` 는 F1 함수가 같은 트랜잭션에서 남긴다(source `auto`).
- 과거 `testItemAssignee` 행의 값(`…: 담당자 1` 등)은 고치지 않는다.

## 9. 배포

- 마이그레이션 **`0050_item_reassign.sql`** (함수 추가 + 실행 권한 + 인덱스 1개. 테이블 구조·기존 데이터 변경 없음).
  0045 헤더 형식, **Supabase 대시보드 > SQL Editor 수동 적용**, idempotent, `begin … commit`, `supabase db push` 금지, 끝에 `notify pgrst, 'reload schema';`.
- 파일 안 순서: ⓪ 의존 확인(§0) → ⓪' 초안 5인자 시그니처 `drop function if exists` → ① 인덱스 → ② `reassign_job_item` → ③ 실행 권한 → commit → notify. 인덱스 생성 동안 `qc_job_items` 쓰기가 잠시 막히므로 업무 시간 외에 적용한다.
- 의존: 0010·0027·0029·0030·0040·0047(잠금 순서 규약)·**0048**·**0049**.
- **전체 적용 순서**: SQL `0048` → `0049` → `0050` → 앱 배포 → `0049` 재동기화 블록 실행. `main` push 가 운영 배포이므로 통합 전에는 `main` 에 올리지 않는다.
  **F3(0049)와 반드시 같은 릴리스** — 작업 시작 뒤 추가된 담당자가 항목을 넘겨받는 길은 이 기능뿐이다.

- 함수 안 상태 문자열은 `types/qc-status.ts` 와 짝을 주석으로 적었다.
