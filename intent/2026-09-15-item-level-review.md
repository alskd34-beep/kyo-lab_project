# Intent: 검토를 작업 단위에서 시험항목 단위로 바꾼다
Author: kyo (개발) · Status: approved
승인: 2026-09-15 사용자 사전 승인(오케스트레이션 작업 지시)

## Problem
사용자 요청 원문:
> 현재 시험자가 모든 시험항목이 종료되어야 검토단계로 넘어가는데 시험항목이 한개가 종료되면 검토를 할 수 있도록
> 개별적으로 변경해줘. 그리고 모든 시험검토가 다 종료되면 검토중 단계에서 승인전 단계로 넘어가도록 해줘.
> 추가로 한개라도 검토 중 단계가 되면 검토중으로 변경하고, 기능을 개선해줘.

지금 검토는 **작업 하나를 통째로** 다룬다. 시험자가 시험항목을 전부 완료해야 작업이 검토전으로 넘어가고,
관리자는 그때부터 작업 단위로 [검토 시작]·[검토 완료]를 누른다. 그래서:

- 시험항목 5개 중 4개가 끝나도 마지막 1개가 며칠 걸리면 **끝난 4개의 검토가 그 사이 전부 멈춘다.**
  검토자는 이미 나온 결과를 보고도 기록을 남길 수 없다.
- 검토 기록이 작업에 하나뿐이라 **어느 시험항목을 누가 언제 검토했는지** 남지 않는다.
- 검토 단계에 들어간 작업은 시험자가 시험항목을 조작할 수 없게 막혀 있어, 검토를 먼저 시작하면
  남은 항목의 시험이 막히는 구조다. 반대로 작업 단위 [검토 완료]는 시험 중인 항목이 있어도 눌린다.
- 관리자가 "승인완료 → 진행중(다시 실시)"으로 되돌려도 되돌릴 시험항목이 없어 자동 전환이 다시 일어나지 않는
  막다른 상태가 된다. 특정 항목만 다시 시험하게 할 방법이 없다.

## Proposed outcome
- 관리자는 **완료된 시험항목마다** 검토를 시작·완료할 수 있다. 다른 항목이 아직 시험 중이어도 된다.
- 작업 단계는 시험항목들의 상태를 보고 서버가 스스로 맞춘다.
  - 시험항목 중 **하나라도 검토가 시작되면** 작업은 **검토중**이 된다(남은 항목이 시험 중이어도).
  - **모든 시험항목의 검토가 끝나면** 작업은 **승인전**이 된다.
  - 전 항목이 완료됐는데 검토가 하나도 시작되지 않았으면 **검토전**, 그 외에는 **진행중**이다.
  - 검토 취소·재실시로 조건이 깨지면 작업 단계도 **뒤로** 맞춰지며, 이력에 원인 시험항목이 남는다.
- 검토중인 작업에서도 시험자는 **아직 검토가 시작되지 않은** 자기 시험항목을 계속 시작·완료할 수 있다.
- 관리자는 시험항목 하나를 **사유와 함께 재실시**시킬 수 있다. 원래 시험 기록(시각·소요시간·검토자)은 이력에 남는다.
- 승인(승인전 → 승인완료)은 지금처럼 관리자가 작업 단위로 직접 누른다.
- 작업 단위 [검토 시작]·[검토 완료] 버튼은 없어지고, 관리자 작업 패널의 시험항목 행에서 검토한다.
  완료 항목 전체를 한 번에 검토 시작/완료하는 편의 버튼이 있다(기록은 항목마다 남는다).
- 시험자 할 일 화면에서는 자기 시험항목의 검토 상태를 볼 수 있다(조작은 못 한다).
- 이 기능 도입 전에 이미 검토중·승인전·승인완료였던 작업은 도입 후에도 같은 단계로 보인다.

## Affected users and systems
- 역할: **관리자**(항목 검토 시작·완료·취소·재실시, 일괄 편의 버튼, 승인) · **시험자**(검토 상태 열람,
  검토중 작업에서도 미검토 항목 시험 조작 가능, 수행일자 수정 가능 단계 확대). 검토 조작은 관리자만 한다.
- 화면: `/product-test/prod-status`(작업자 작업 현황 — 오른쪽 작업 패널의 항목 행·단계 막대·상태 컨트롤) ·
  `/test-mgmt/test-status`(시험현황 상세 서랍) · `/my-tasks`(할 일 — 항목 검토 배지, 단계 전환 안내 문구, 동시분석 그룹 카드 묶기).
- 테이블: `qc_job_items`(검토 상태·검토자·시각) · 신규 시험항목 검토 이력 테이블 · `qc_jobs`(단계 자동 도출) ·
  `qc_job_status_history`(자동 전환 이력) · `pct_orders`(오더 상태 동기화) · `notifications`(단계 전환 알림).
- 마이그레이션: **1건(0048 — 컬럼·제약·이력 테이블·DB 함수 추가 + 기존 작업 백필). Supabase SQL Editor 에서 수동 적용이 필요**하며,
  적용 전에는 항목 검토 동작과 검토 상태 조회가 안내 메시지와 함께 거절된다.
- 확정(LOCK)·작업 시작 상태와의 관계:
  - **작업 단계 전이 규칙이 바뀐다** — 검토전·검토중·승인전은 사람이 버튼으로 넘기는 단계가 아니라 항목 상태에서
    도출되는 단계가 되고, 뒤로 가는 자동 전이가 새로 생긴다.
  - `지연`·`승인완료` 작업은 자동 도출하지 않는다(지연은 사람이 지정하고 푸는 표시, 승인완료는 수동 종결).
  - 관리자의 작업 상태 직접 변경은 항목 상태와 맞는 단계로만 허용된다(지연 지정·해제, 승인전↔승인완료는 예외).
  - LOCK 은 일정 자동 변경 금지일 뿐이라 검토 동작과 무관하다. LOCK 오더의 작업도 똑같이 검토한다.
  - 오더 상태는 지금 규칙(지연 우선 → 가장 덜 진행된 작업 단계 → 미시작 담당자 상한) 그대로 작업 단계에서 계산된다.
- 크론: 직접 바꾸지 않는다. PCT 적재(09:00/14:00)는 진행 단계 오더를 자동 갱신하지 않는 기존 규칙 그대로이고,
  장비 대기 자동취소(매시 정각)와 무관하다. 작업 단계를 시간이 지나 자동으로 바꾸는 크론은 만들지 않는다.
- 함께 가는 변경: 병렬 배정(2026-09-15-parallel-assignment)과 진행 중 시험항목 담당자 변경(2026-09-15-in-progress-item-reassign)이
  이 기능의 단계 도출 규칙을 그대로 쓴다.

## Constraints
- **시험 진행 상태(대기·진행 중·완료)의 의미를 바꾸지 않는다.** "완료"는 계속 "시험이 끝났다"를 뜻해야 하며,
  항목별 실소요 통계·동시분석 절감·운영 리포트·완료 개수 KPI 의 숫자가 이 변경 때문에 달라지면 안 된다.
- 작업 단계를 정하는 규칙은 **한 곳에만** 있어야 한다. 화면·서버·DB 가 서로 다른 규칙으로 단계를 계산하면 안 된다.
- 검토 기록이 남지 않으면 검토도 일어나지 않아야 한다(GMP/ALCOA+). 검토 동작·항목 갱신·이력·단계 전환은 함께 성공하거나 함께 실패한다.
- 재실시로 지워지는 시험 기록(시작·완료 시각·소요시간·검토자)은 **이력에 원본 그대로** 남긴다.
- 기존 작업 백필은 **지어내지 않는다** — 누가 언제 검토했는지 모르는 기존 작업은 검토자·시각을 비워 두고 "백필"임을 표시한다.
- 시험자가 자기 작업 상태를 바꿀 수 있는 범위(진행중↔지연)는 넓어지지 않는다. 시험자가 검토중 작업을 진행중으로 되돌릴 수 없어야 한다.
- 최종 허용 판정은 서버가 한다. 화면의 버튼 숨김만으로 막지 않는다.
- 슬랙·앱 알림은 **작업 단계가 실제로 바뀐 경우에만** 보낸다. 항목 검토마다 보내지 않는다.
- 작업 시작 취소(0047)의 판정 규칙은 바꾸지 않는다.
- 운영 배포는 `main` push 다. 병렬 배정·항목 담당자 변경과 통합이 끝나기 전에는 `main` 에 올리지 않고,
  SQL 0048 → 0049 → 0050 적용 뒤 앱을 배포한다.

## Open questions
- **오더 수준에서도 "하나라도 검토중이면 검토중"이어야 하나?** 이번에는 오더 상태 규칙(가장 덜 진행된 작업 단계)을 그대로 두어,
  병렬 배정에서 한 담당자 작업이 검토중이어도 다른 담당자가 진행중이면 오더는 진행중으로 보인다. 사용자 원문이 오더까지 뜻했는지 확인이 필요하다.
- **수행자 본인 검토 금지**를 넣을 것인가? 이번에는 막지 않고 검토자만 기록한다. 관리자이면서 시험자로 연결된 계정이 운영에 실제로 있는지 모른다.
- 재실시는 "항목 초기화 + 원 기록은 이력"으로 정했지만, 재실시가 일탈(OOS/CAPA) 기록과 연결돼야 하는지는 정하지 않았다.
- 구현 세부 중 결정되지 않은 것(검토 이력 보존 방식, 지연 해제 때의 단계 불일치, 일괄 검토의 처리 단위 등)은
  spec 의 「확인 필요」 절에 모았다. 구현 전에 그 목록부터 답을 받는다.
